### 1. 便宜模型先分類分群，大模型只做洞察
分類、分群、路由這類有限選項的任務，可交給便宜又快的決策模型，聰明的大模型只處理分好的重點。例如 Jev 約 1,700 個 PR（1.7 萬組配對）花約 9 美分，Cloudflare Auto Router 也依請求難度與風險選模型。實作上先找出程式裡的 if/else 分類點，單層不準就多加一層，再用較聰明的 LLM 抽樣驗證。

### 2. 必做的規則交給程式碼，不要全塞進 prompt
指令一多，模型就會漏，IFScale 顯示 20 個模型在 500 條指令下，最好的也只遵守 68%。做法是把一定要執行的步驟寫成確定性程式碼（如 before_reasoning 區塊），並由程式決定哪些資料進 context，模型只負責推理。

_類型：framework_

### 3. 用不同於寫碼的模型來審查
讓與寫碼者不同家的模型做 code review，可降低同源盲點。Greptile 實測換用另一家模型審查，重大問題捕獲率高約 10%；另外歷史事故 PR 資料集能讓你在改 prompt 或換小模型時，知道有沒有漏抓。

### 4. 評估 agent 只驗結果，不管過程
把 agent 放進乾淨沙箱，由 verifier 在跑完後才檢查留下的副作用，與 agent 實作解耦，因此能在固定 task 下放心重構。先用人寫的 oracle 解答驗證環境與 verifier 沒問題，再讓 agent 上場，可省下 token 並建立對評測本身的信心。

_類型：technique_

### 5. 一次發布只驗證一個全新的點子
把每個功能標成 Proven（照抄已有效）、Better（10 個現有用戶中 10 個都認為更好）或 New（其餘），讓一次發布只押一個 New，失敗時才知道原因。平台轉換早期 New 應越少越好，例如 Hay Day 對 FarmVille 2 以「0% new」勝出。
