## [FREE] 70% of analytical systems will adopt this open-source solution (?)

介紹 Apache Arrow DataFusion：一套模組化、可擴充的查詢引擎，讓開發者不必從零打造分析型資料庫。 **Why** 建構分析資料庫（儲存、記憶體表示、查詢最佳化、實體執行）非常耗時昂貴，通常只有大公司做得起。 **How** DataFusion 建立在 Parquet（磁碟）、Arrow（記憶體）與 Rust 之上，包含 catalog、SQL／DataFrame 前端、可擴充的邏輯與實體計畫改寫、以 Arrow RecordBatch（預設 8192 列）進行串流且 pull-based 的執行，並用 Tokio 排程。catalog、函式、optimizer、operator、前端與執行環境皆有擴充點。 **What** 文中列出的採用者包括 Cloudflare R2 SQL、Datadog、InfluxDB、OpenObserve、Pydantic Logfire、Spice AI、LanceDB、ParadeDB 與 Cube；另有 DataFusion Comet 加速 Spark、StreamFusion 加速 Flink，Delta Lake 與 Iceberg 的 Rust 函式庫也使用它。記憶體管理內建 Greedy 與 Fair 兩種 pool。

### 重點
- DataFusion 三大基石為 Parquet、Arrow、Rust；執行採 pull-based 串流，每批為 Arrow RecordBatch（預設 8192 列），以 Tokio 做 CPU 與 I/O 排程
- 可擴充點涵蓋 catalog、自訂函式（scalar／aggregate／window）、optimizer 改寫順序與邏輯、自訂 operator（如 IOx 的時序補值）、自訂前端與執行環境；記憶體 pool 有 Greedy 與 Fair 兩種
- 加速器用法：DataFusion Comet 用原生 Rust 執行 Spark 運算子、StreamFusion 加速 Flink，計畫由原引擎產生、Arrow 與 DataFusion 負責記憶體表示與實體執行

Architecture At a high level, DataFusions looks like a database with typical components: the catalog, front end, optimizer, and execution engine. Catalog Every database needs a catalog to provide information such as: &#8220;Does this table exist&#8220; &#8220;If yes, do these columns exist&#8220; &#8220;If yes, what are their types and statistical information&#8220; &#8230; DataFusion supports simple in-memory and Hive-style catalogs. Front ends For the data type system, DataFusion uses Arrow directly. From integer, floating-point numerics, fixed-precision decimals, variable-length strings, dates, times, timestamps, intervals, duration types to nested data. Workers present and exchange data in Arrow format or scalar values. &#8212; For the SQL query parser, DataFusion leverages the sqlparser-rs library to parse input SQL text into a logical plan. The library supports nearly all the SQL features: from SELECT, WHERE, GROUP BY, JOIN to INTERSECT or GROUPING SETS. Besides SQL, DataFusion also provides the DataFrame API. It parses the input DataFrame expressions into logical plans and executes them the same way it does with SQL queries. &#8212; DataFusion supports all structures needed to evaluate the expression tree and relational operators. It also includes libraries to serialize/deserialize these structures for efficient network exchange. For query plan rewriting, it includes an extensible rewriting framework with a chain of logical and physical plan rewrites. These rewrites handle filter pushdown, projection (selection) pushdown, leveraging the physical layout (such as clustering), and reordering joins based on statistics. For aggregation, DataFusion provides a huge library of scalar, window, and aggregate functions. The execution engine In most cases, DataFusion executes the physical plan in streaming fashion. As discussed in the previous DuckDB and Polars articles, streaming execution loads and exchanges data incrementally to keep the memory usage controllable. Each operator will actively wait for its parent&#8217;s output batches (pull-based approach), which are Arrow RecordBatches with a default size of 8192 rows. &#8212; Each step in the physical plan can run in parallel across CPU cores. This number of parallel tasks per step is called partitioning and is defined at plan time. Take a filter step with 4 partitions. This creates 4 separate filter tasks, each running on its own slice of the data. &#8212; So a step can run in parallel, but how DataFusion decides which tasks run on which cores. DataFusion handles thread scheduling by using Tokio, Rust's most popular async runtime. Although Tokio was designed for asycn I/O, with features such as work-stealing mechanisms and excellent performance even for CPU-intensive tasks, DataFusion still uses Tokio for both CPU and I/O tasks. &#8212; DataFusion manages memory using the memory pool. DataFusion ships with two built-in pools: Greedy: It doesn&#8217;t try to split resources fairly among the operators in a query. First come, first served. Fair: It splits memory evenly. Extensibility The key point about DataFusion is that most of what we discussed above is extensible. Catalog For specific use cases, users can use the Catalog API to customize the catalog to work for their needs, such as defining a new kind of table or schema. Functions Besides built-in functions, DataFusion exposes an API for defining all kinds of custom functions at the same performance level as the built-in ones. From scalar functions with one output row per input row, to aggregate functions with one output for multiple inputs, to window functions that require reaching all rows in the window range. Optimizer Recalled that DataFusion could rewrite the logical plan multiple times to output the final physical plan. Users can define the order of rewrites and the rewrite logic itself to customize plan-optimization behavior. Operators Although DataFusion supports all the relational operations, a specific database might require domain-specific operators. No problem, since you can also extend the supported operators with DataFusion. For example, IOx, the InfluxDB time-series engine, extended DataFusion to support specialized time-series gap filling. The new query frontend If the database solution doesn&#8217;t prefer SQL, engineers can skip the DataFusion SQL frontend and implement their own front end, as long as it creates the same logical plan structure. Execution Environment DataFusion also offers APIs for low-level resource customization: memory pools, disk management, and caching. Use cases Although DataFusion can work as a standalone query engine like DuckDB or Polars, it&#8217;s not famous for that. Data end users might not have heard about it at all. However, with data infrastructure builders, DataFusion is a star. Its performance, powered by state-of-the-art techniques, ecosystem compatibility through Parquet and Arrow, and, most importantly, its extensibility make DataFusion a compelling choice for building new analytical databases or systems. Those projects, in theory, will spend more time on the customized features rather than re-implementing existing analytic engine techniques (e.g., vectorized execution, query optimization, scheduling tasks&#8230;) Some famous DataFusion adoptions are: Cloudflare R2 SQL is the distributed engine Cloudflare built. Their engineers use Apache DataFusion as the query engine inside each R2 SQL worker, letting DataFusion handle the heavy lifting of query execution. Datadog &#8220; chooses DataFusion as a single composable query engine to replace previously specialized query systems &#8221; InfluxDB is one of the earliest adopters. It is a well-known open-source time-series database developed by InfluxData. OpenObserve is an open-source observability platform that aims to provide an alternative to tools like Datadog. The project leverages DataFusion for high-performance Parquet file reading directly in object storage. Pydantic Logfire is an observability platform built by the team behind Pydantic, the most widely used Python data validation library. Logfire ingests OpenTelemetry traces and logs into Parquet files and uses DataFusion as the SQL explorer interface. Spice AI is an AI agent and application platform that embeds DataFusion to execute federated queries across more than 30 remote data sources, caching high-speed data locally for LLM memory architectures. LanceDB is a developer-friendly vector database for AI and multimodal data. It uses DataFusion to run fast analytical queries over Lance, a new columnar format that aims to challenge Parquet.
