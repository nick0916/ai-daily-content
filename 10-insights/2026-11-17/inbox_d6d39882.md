## Inference engineering for software engineers

教軟體工程師如何從 frontier lab 的 API 搬到開源模型的推論服務，並降低成本。

**Why** 企業想壓低 AI 開支：文中提到 Uber 每 token 成本降約 50%、Pinterest 90%、AT&T 56%；另外 frontier lab 自報 uptime 低於雲端慣例的四個 9，且多租戶下效能劣化客戶端無從得知。

**How** 分兩階段：先把 API 換成推論供應商的多租戶端點（相容 OpenAI/Anthropic 格式），遇到 rate limit、效能不穩、費用過高再改用專屬 GPU，需設定模型大小、KV cache、failover，並可用 speculative decoding 提升 decode 階段效率；選模型時用自家 eval set 而非通用 benchmark。

**What** 文章訪談 Modal、Fireworks AI、Baseten 三家供應商：Modal 重程式化 SDK 與開源，Fireworks 主打專屬部署與微調（如基於 Kimi K3 後訓練的 Ember-1，據稱推理 token 少 40%），Baseten 主打 agent 平台。Anthropic 自報 uptime 99.5%、OpenAI API 99.97%、ChatGPT 99.2%；常見做法是用帶 fallback 的 LLM gateway。（內文被截斷，後半段未涵蓋。）

### 重點
- 成本案例：Uber 每 token 成本降約 50%、Pinterest 90%、AT&T 56%；Revolut 自建 56 台 B200
- 兩階段路徑：多租戶 API 替換 → 遇 rate limit/效能不穩/費用高再上專屬 GPU（KV cache、failover、speculative decoding）
- 選模型靠自家 eval set 或 prompt 樣本，不靠通用 benchmark；約 10% Modal 客戶會做到微調（Modal 說法）

A recent trend we’ve covered is of tech companies moving to open models to rein in AI spend: Uber cut its per-token costs by 50%, Pinterest by 90%, and even AT&T has achieved a 56% decrease. But how do you move from a frontier lab’s APIs to using open models? There are two options: “Bare metal:” With plenty of time and money, you can go “bare metal” and purchase a few dozen NVIDIA GPUs and use those AI supercomputers, like Revolut has done : running 56 separate B200 units itself to serve its inference needs. This is a lot of work to set it up, but after that, operational costs are as cheap as it gets. Inference provider: most companies contract with an inference provider that operates large fleets of GPUs, and makes it easy for customers to onboard and start using open models fast. Onboarding to an inference provider to run LLM workloads comes with challenges, such as dealing with tail latencies, worrying about cache hit rates, rate limits, and more. Inference engineering is a set of engineering practices that we believe is increasingly beneficial for software engineers to familiarize themselves with. To go deeper into this area, we’ve talked with three leading inference providers to learn more: Modal , Fireworks AI , and Baseten . Today, we cover: What are inference providers & how do they differ from AI labs? They have GPU infrastructure similar to frontier labs, don’t train their own frontier models and are experts at hosting open models. When to switch from frontier labs? The most common reasons are to reduce costs, have more control over latency, and to fine-tune AI models. Choosing a model, provider, and deployment strategy. Use evals to find the right open model for your use case, evaluate vendors, and decide between multi-tenant API usage and dedicated GPUs. Stage #1: API replacement using a multi-tenant inference setup . The easiest way to onboard to an inference provider is to “swap” the API of a frontier lab to an API of an inference provider. But there may be latency problems and caching issues at high loads. Signs you’ve outgrown multi-tenant inference APIs. Hitting rate limits, performance consistency problems, and overpaying for usage are signs that it might be time to adopt dedicated GPUs. Stage #2: Configuring dedicated GPU nodes. With dedicated GPUs, you’ll need to get into the details: size of the model, interactivity versus throughput, KV cache sizing, failover options, and more. Speculative decoding. If there’s unused compute during the decode phase, you might consider a Speculator to further boost inference performance. What are inference providers & how do they differ from AI labs? Inference providers are companies that sell access to LLMs which they run on users’ behalf. From the outside, this isn’t so different to what OpenAI and Anthropic offer: an API endpoint, ability to stream tokens, and pay based on token usage. But what makes inference providers different from frontier labs is the models running behind the endpoint: inference providers run open-weight models, whereas frontier labs train their own models. In this field, Modal, Fireworks, and Baseten each operate slightly different strategies: Modal sees itself as a cloud infrastructure provider that focuses on making its offering programmable via its SDKs. It natively supports inference services through its SDKs, but leans heavily on the open source ecosystem for running its inference workloads efficiently. Performance tweaks to its stack are merged upstream. In the words of Richard Gong, Inference Lead at Modal: “when you run code on Modal, you should be able to see all the code that’s running.” Fireworks positions itself as a provider for specialized AI workloads. Most of its business is in dedicated deployments, which often include fine-tuning and provision of latency guarantees. Much fine-tuning and post-training is available for self-service. Fireworks also offers forward-deployed researchers that can help with post-training custom models or components. Dmytro Dzhulgakov, Fireworks’ CTO, says: “our tagline is specialized intelligence, which means we will tune everything from model to infrastructure for your particular use case.” Baseten describes itself as an all-in-one place to build agents. It starts with the basic infrastructure layer with uptime guarantees, flexible commercial terms, without vendor lock-in. Baseten builds additional layers for building agentic workloads on top of its inference platform. These additional layers include sandboxes, governance services, and self-serving, post-training functionality. To customers, inference providers offer LLM APIs that can be used as drop-in replacements for frontier labs’ APIs. However, inference providers are not the same, as suggested above: Inference providers don’t pre-train their own foundational models . A single pre-training run for frontier-level LLMs can cost millions of dollars, and only hyperscalers and specialized frontier labs can afford it. Inference providers run post-training on open-weight models because it’s significantly cheaper. Competitive pricing. The main business of inference providers is offering open-weight models at competitive rates. Dedicated hardware. A big part of the appeal of inference providers is the ability to have dedicated hardware for users to interact with vendors on the infrastructure layer. Efficiency & customization. Inference providers offer similar commoditized open models, and compete heavily on efficiency and customization services. As an example of efficiency, Fireworks announced its Ember-1 model in September 2026, that is post-trained on the Kimi K3 foundation, delivering a similar quality level but with 40% fewer reasoning tokens consumed. Consuming far fewer reasoning tokens gives Fireworks an edge on cost compared to a vanilla Kimi K3 model. In general, frontier labs have poor uptime, and this helps inference vendors win market share. API Uptime provided by frontier labs isn’t at the levels expected of modern cloud providers: currently, the self-declared uptime of Anthropic is 99.5%, and for OpenAI it’s 99.97% for API, and 99.2% for ChatGPT. These numbers are well below the four nines (99.99%+) uptime expected of cloud providers – which is something that a vendor like AWS is known to uphold . Frontier labs’ API uptime. Reliability is an ongoing concern with the LLMs of frontier providers and inference providers. Even though many inference vendors offer higher reliability guarantees than frontier models, inference providers can also go down, too. For companies that use inference providers, it’s common to use an LLM gateway with fallback logic to another provider – or to a frontier API. We explored this in a deepdive with Ramp , whose LLM router project started with this exact problem statement. 2. When to switch from frontier labs? Moving from frontier AI labs to an independent inference provider is often driven by three factors: cost, control, and the need for more customization. Most common reason: cost Many companies start considering inference providers because they have pressing cost concerns. In many cases, a frontier model is more capable than necessary for most requests, meaning a “dumber” model is just as good for simpler tasks – and nobody would notice the difference! In such cases, it’s a “no-brainer” for an engineering team to choose to route some requests to a cheaper model hosted by an inference provider. “Smart routing” is an obvious way to cut costs. An LLM router – the “smart router” – is prompt-aware and can route an LLM request to the most cost-efficient provider that can solve the request. This is an approach that fuelled Uber’s ~50% cut in per-token costs this summer . Providers offer OpenAI/Anthropic-compatible API endpoints, so switching providers is trivial. All that is needed is to point your app at the new endpoint operated by a “smart router.” But how to decide which model to serve? Generic benchmarks are often insufficient because they usually do not fully represent a team’s traffic patterns. Most inference providers ask for prompt samples or eval sets in order to gauge which model best serves a customer’s use case. The experience of using a new LLM endpoint resembles using APIs provided by frontier labs, while API calls are still charged per token, and response time SLAs generally don’t exist. More control over latency When you use a frontier lab’s endpoint, there is little control over operational issues like response latency and model availability. Opting for a dedicated setup with an inference provider offers full control over both: Latency : model response times are more predictable because the app has dedicated capacity that can scale by usage. Model availability : Engineers can run the model of their choosing on their dedicated GPUs and keep operating it as long as needed, avoiding the risk of a frontier lab changing models from one day to the next. Fine-tuning model quality: customization When an inference stack runs on dedicated hardware with open source models, it’s possible to work with inference providers to finetune a model’s quality as required, which optimizes latency or throughput performance. Richard Gong of Modal says that around 10% of their customers go this far, suggesting that customization is for “power users”. Fine-tuning a model’s quality is typical in two scenarios: Tweaking a smaller model : achieving a similar level of quality with a smaller model, with fewer parameters. This performance gain is achieved via performance tweaks not possible with off-the-shelf models. Inference providers allow you to post-train a smaller model for your specific use case. A post-trained small model can then outperform the original model in those specialized scenarios. Fine tuning for niche use cases. Improving quality when general purpose models aren’t good enough, often because the data isn’t publicly available. For example, projects in the legal and medical sectors tend to benefit from this, according to the Fireworks team. 3. Choosing a model, provider, and deployment strategy Most inference providers offer the exact same models to run, and the differences lie in model performance and quality. For example, model quality can differ by default context length, and some providers cap this to below what the model supports. There’s also quantization to consider, where a model’s weights are compressed to a lower numerical precision, or default temperature aka controlling how random the output is.
