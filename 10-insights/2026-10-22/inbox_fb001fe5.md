## [FREE] A file format claims to be 100x faster than Parquet

說明 Lance 檔案格式如何改掉 Parquet 的設計，讓 AI 工作負載常見的隨機讀取更快。

**Why** AI 工作負載（向量、影像、文件）需要用語意搜尋撈取少數幾列，但 Parquet 擅長順序掃描；其最小讀取單位是 page，只想取一列也得讀出並解碼整個 page。此外 FileMetadata 需整份反序列化才能取得單一欄位 schema，而 row group 需整個緩衝在記憶體再寫出，容易造成 OOM。

**How** Lance 依值大小選擇編碼：小值用 mini-block（約 4–8 KiB 的 chunk，最多 4,096 個值），大值（門檻 256 bytes）用 full-zip，只允許可單獨解碼的「transparent」編碼。它捨棄 row group，每欄各自分頁（預設 8MB），頁面以絕對 offset 定位；每欄的 metadata 為獨立 protobuf message，因此能直接讀取所需欄位。

**What** Lance 由 LanceDB（YC W22）約 2022 年推出，宣稱隨機存取比 Parquet 快 100 倍（此為文中所述的宣稱）。文中例子：100 萬列的檔案中，boolean 欄約 128 KiB 可放進單一 page，3 KiB 的 embedding 欄約 3 GiB、約 384 頁。讀取端可在任意列邊界切分檔案平行處理。

### 重點
- Parquet 三個痛點：以 page 為最小讀取單位導致隨機讀取延遲高；FileMetadata 需整份反序列化（機器學習表可達上萬欄）；row group 須整個緩衝在記憶體且所有欄位共用列數，大值欄位會拖累其他欄
- Lance 的頁面編碼：mini-block 用於小值，full-zip 用於 ≥256 bytes 的大值且只用 transparent 編碼（如 dictionary 可單值解碼，delta 則須解碼前面所有值）
- Lance 取消 row group，每欄獨立分頁（預設 8MB），每欄 metadata 為獨立 protobuf，欄位 schema 可 O(1) 取得，並能在任意列邊界切分平行讀取

The row-group constraint The row group in Parquet is tied directly to the physical I/O unit. The write engine cannot flush a partial column chunk, so it must buffer the entire row group in memory before writing. This is a common cause of out-of-memory (OOM) failures, especially with large column values like AI vector embeddings. Even without OOM, you may still run into other problems when storing a very large column. Imagine one column with 4KiB values (e.g., 4,096 bytes); a 512 MB Row Group would contain only 125,000 rows (512,000,000/4,096). Because all columns in the row group must have the same number of rows, all other columns must also be capped at 125,000 rows, although an Int32 column could have 128 million rows (512,000,000/8). Because each row group will be small, the Parquet file must contain many row groups. This could be inefficient: More metadata to manage More, smaller reads: within a row group, columns are stored one after another. Reading one column across many row groups means many separate, non-adjacent reads. Reading data from disk is best when it's as sequential as possible, but more row groups don&#8217;t encourage that. More reads also mean more GET object storage requests. Ineffective compression: large row groups provide a larger sample size of data for each column, allowing compression and encoding algorithms to be more effective. Lance Lance is a modern, open-source columnar data format designed for machine learning and multimodal AI, launched around 2022 by LanceDB (a YC W22 startup) to address Apache Parquet&#8217;s performance limitations in AI workloads. In the Lance spec, there are roughly 4 sections: The data pages: each page holds some or all of one column&#8217;s data. Every page in the file is located by an absolute offset. The column metadata: it provides information about the data pages and is located near the end of the file. It includes a set of protobuf messages; each column has its own message, including information such as pointers to the data pages or the encoding scheme. A column metadata offset table &nbsp; provides the position and size of each column&#8217;s metadata message. It&#8217;s stored right next to the column metadata. The offset array and the footer live at the end of the file. The array contains the offset to the column metadata, and the footer contains the offset to the array. Page Layout Lance handles random access differently depending on value size. For small values like integers and short strings, Lance uses mini-block encoding. The data page is organized into chunks; each is around 4&#8211;8 KiB, with at most 4,096 values. Like Parquet&#8217;s page, the engine still reads and decodes a chunk to get one value. However, because it's much smaller, the decoding is faster. For large values (vector embeddings, images, large text, 256 bytes per value as threshold), Lance uses &#8220; full-zip &#8221; encoding, which interleaves each value&#8217;s metadata directly with its data and stitches these metadata-data buffers right next to each other. The compression used is restricted to &#8220;transparent&#8221; encodings, meaning you can decompress a single value without decoding neighboring values. So if you need embedding #48, you jump directly to it and decompress just that one value. &#8212; With transparent encoding, you can decode each value on its own, as long as you know where it is. Example: Dictionary: ["red","blue","red","green"] becomes indices [0, 1, 0, 2] . Index #3 is 2 , which maps to "green" . With &nbsp;opaque encoding, decoding one value requires decoding other values too. Example: Delta: [100, 102, 105, 106] stored as base 100 plus differences [2, 3, 1] . Value #3 = 100 + 2 + 3 + 1, so you need every difference before it. Opaque encodings could save more space, but the values depend on each other, so you can&#8217;t decode just one. Mini-block can use opaque encodings, while full-zip is strictly limited to transparent encodings. Abandon Row Group The Lance file structure abandons the row group concept completely. The column&#8217;s data is stored across multiple disk pages. Each page defaults to 8MB. Different columns can have different numbers of pages. Because a page is referenced by an absolute offset, Lance doesn&#8217;t require the pages in the same column to be contiguous. This gives a freedom Parquet can&#8217;t offer: the writer can use separate buffers for each column instead of buffering the whole row-group. Each column's page count simply follows its data size. Take a file with 1 million rows. A boolean column is about 128 KiB, so it fits in a single page. A 3 KiB embedding column is about 3 GiB, which becomes roughly 384 pages of 8 MiB each. No longer does every column have to share the same row group size. &#8212; The same freedom applies on the read side. In Parquet, the row group is usually the unit of parallelism. Ten threads usually means ten row groups. If a file has only one big row group, there&#8217;s not much to split. Lance lets you split the file at any row boundary. Say two threads share a 2 million-row file. One reads rows 0 to 999,999; the other reads from 1,000,000. Row 1,000,000 might sit in the middle of a page, but that&#8217;s not the problem. Each page records the row it starts at, and its internal layout (mini-block chunks, or full-zip byte offsets) maps any range of rows to a range of bytes. So each thread reads only its own page slice by locating the required byte.
