## A Valid Key Let an AI Agent Delete Production - Sagar Batchu, Speakeasy

給 AI agent 一把有效的金鑰不等於允許它做任何事，必須在 agent 和 API 之間加一層身分、政策與紀錄的控制層。

**Why** 今年四月有新創創辦人請 coding agent 修 staging 的憑證問題，agent 在無關檔案中找到權限過大的 token，把 production 資料庫連同備份在約 10 秒內刪光；沒有漏洞、沒有 prompt injection，只是有效憑證加上錯誤判斷，中間沒有任何防線。

**How** 四步架構：Connect（所有呼叫走單一入口，如 MCP gateway）、Identify（agent 自成主體，並記錄 operator 與授權人）、Decide（allow/deny/quarantine/escalate）、Record（行動前先記錄並綁定 agent 身分）。權限判斷取憑證上限 C、agent 自身政策 A、owner 即時政策 O 三者交集，A 與 O 每次呼叫都重新讀取，撤權下一次請求就生效。

**What** 講者 Sagar Batchu 是 Speakeasy 共同創辦人，該公司的 AI control plane 位於關鍵路徑上，身分來自 Okta 等 IdP，透過 MDM 派送、新員工開箱即用，延遲目標 100 毫秒內。他引用的數據是 82% 的組織已在跑 AI agent、只有 32% 有 AI 治理政策、shadow AI 造成的外洩平均成本約 500 萬美元。

### 重點
- 權限 = 憑證上限 ∩ agent 自身政策 ∩ owner 即時政策：即使 owner 能刪 production，只被授權 staging 的 agent 也刪不了；反之亦然
- 身分模型分三種角色：agent（主體）、operator（驅動動作，只做歸因、不擴權）、authorizer（核准憑證的人，憑證生命週期內固定）
- 數據：82% 組織已用 agent、32% 有治理政策、shadow AI 外洩平均成本約 500 萬美元；治理路徑要比未治理路徑更容易走，團隊才不會繞過
