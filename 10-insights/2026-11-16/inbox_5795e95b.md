## How Instacart Uses LLMs to Make People Buy More

Instacart 用 LLM 把使用者隨手打的搜尋字，轉成可用來找商品的類別、改寫查詢與結構化標籤。

**Why** 使用者常打「bread no gluten」這類與商品目錄用字不同的查詢；舊做法依賴點擊與購買行為訓練，資料雜訊多、長尾查詢樣本少，且分類、改寫等多套系統各自維護、對同一查詢解讀不一致。

**How** 用 RAG 把目錄與歷史購買模式放進 prompt、對輸出做後處理 guardrail，並以自家範例微調小模型。類別預測分三階段：歷史資料提候選、LLM 重新排序、再用 embedding 相似度過濾不相關結果。改寫則拆成同義詞、放寬、替代品三種，各有專屬 prompt 與範例。

**What** Instacart 的查詢理解（QU）改造：舊改寫系統僅涵蓋約 50% 搜尋流量，新做法提升到超過 95%，三種改寫的精準度皆超過 90%。另包含語意角色標註（SRL），從如「2% chocolate milk」的查詢抽取商品、品牌與屬性。

### 重點
- 類別預測三階段：歷史購買資料提候選 → LLM 重排 → embedding 相似度低於門檻就丟棄
- 查詢改寫拆成同義詞、放寬、替代品三種並各自設計 prompt；涵蓋率由約 50% 提升到超過 95%，精準度超過 90%
- 直接叫 LLM「改寫查詢」效果差（如「1% milk」只變成「one percent milk」），必須指定改寫的目的

The Problem With Instacart’s Initial Approach You can separate product search into 3 broad activities: First, you have QU, which is meant to understand the user’s request. Second is retrieval, where you find a set of relevant products. Third, you have the ranking phase in which you decide the order in which each product is shown to the user. As you can see, information created during the QU phase is the one that guides both retrieval and ranking. For example, let’s say you have a search query that says “bread no gluten”. It refers to bread with a gluten-free attribute. This search phrase gives a very important piece of information to the search setup if you don’t treat the phrase as three unrelated words. At Instacart, the QU phase can produce three types of information. First is the product categories, in which you decide which sections of the catalog are important for answering the query. Second is alternative queries, which deal with other search phrases that might help find suitable products. Third is structured tags. This deals with the parts of the query that might help learn more about the product, its brand, or specific attributes. Instacart already had machine learning systems that helped it understand queries. The problem was how to get it to work consistently for the enormous variety of things that people search for. One way to solve this problem is to analyze search behaviour. But this behaviour provides imperfect training data. A supervised machine learning model learns from examples that are paired with desired answers. For classifying queries, you might connect a search phrase to the correct product category. However, as you might have already noticed, it’s quite difficult to collect all these labels. Instacart can look at searches, clicks, and final purchases. But those actions don’t directly reveal whether the system understood the query in a correct manner. For example, you might have a user who searches for bread but ends up buying bananas. Now, this purchase doesn’t mean that “bread” should be classified as a query about fruits. Of course, behaviour can give some nice evidence, but a relation between a query and a purchase decision can be quite noisy. You can use human reviewers to provide cleaner labels. But this also needs time and money. Also, rare queries have very little history. For example, the user might make a very specific query such as “2% reduced-fat ultra-pasteurized chocolate milk”. If you have a system that learns mostly from historical clicks and purchases, it might not have enough examples to deal with such phrases. These uncommon searches are part of the long tail. While each such query may account for little traffic, together they might represent a large collection of customer requirements. Broad queries also create a different type of problem. For example, let’s say you have a search phrase such as “healthy food”. It can point to so many categories, and the system has to handle ambiguity rather than force the query into a single narrow interpretation. With separate models, you also end up with a lot of maintenance work. Instacart had to maintain different systems for different tasks. For example, they had a category classifier that used a FastText model. The query rewrite system mined patterns from user sessions. Each system needed its own data processing, training, and deployment requirements. This increased maintenance work. And even then, they made inconsistent interpretations of the same query. Therefore, the Instacart engineering team wanted something that could improve their QU and also provide a more consistent foundation for taking care of the other responsibilities. How a General LLM Becomes Useful for Instacart A large language model (LLM) starts off with a broad knowledge of language and the general world. This makes it pretty good at making sense of queries it might have never seen before in the historical data. For example, an LLM might already know that something like “Italian parsley” and “flat parsley” refer to the same thing, and “curly parsley” can act as a substitute. This is all part of the model’s general awareness that it got during training, and it doesn’t need to learn these things from a bunch of examples. Of course, general knowledge doesn’t automatically make the LLM knowledgeable about Instacart’s product catalog and the behaviour of their customers. To bridge this gap, the Instacart engineering team used the following techniques: First, you provide all the relevant information in the prompt to the LLM. This approach is known as context engineering. RAG is the primary method that is used over here. The system pulls in information such as the catalog records and historical patterns and puts that information along with the query. To be clear, RAG here means that you try to give the model all the useful business information before asking the model to make a prediction. Second, the system validates the model’s output. Instacart has implemented post-processing guardrails to check how suitable the output is and how compatible it is with their product catalog. You can have a model generate a plausible answer, but it still doesn’t fit the actual data of the business. Therefore, validation is a separate part of the system. In the third technique, they fine-tune smaller models on their own examples. Fine-tuning means additional training that can change the parameters of the model. Instead of giving all the domain guidance using the prompt every single time, the team teaches the model to work on a particular task with high-quality examples. How Instacart Knows What the Query Is About Instacart has organized its catalog using a hierarchy of categories. For example, you have the following path: Meat → Beef → Beef Ribs → Short Ribs Each step in this category path makes things more specific. If the search system knows the entire path, it can easily identify the relevant part of the catalog. The earlier version of the classifier treated these categories more like a flat collection of labels. For example, in the case of “buttermilk”, it might predict “Dairy” and “Milk” separately, where each label came up with a confidence score. While those predictions were also useful, they didn’t express the full relationship. With the new approach, you combine historical evidence with LLM interpretation and also check the relevance of the product. In this approach, the system first finds the leading categories that are associated with purchases following the query. These categories form the initial set of candidates. The advantage is that this gives the model a starting point linked with Instacart’s own data. Since typical purchase behaviour can be quite erratic, you need to assess the candidates even more. In the next step, you ask the LLM to assess the candidates. The LLM re-ranks the candidate categories using the query and the Instacart context that was given to it. For example, “buttermilk” might map to Dairy followed by Milk and then Buttermilk. On the other hand, something like “vegan roast” might map to Meat followed by Meat Alternatives. As you can see, this is how language understanding and knowledge of the world help understand a query whose wording doesn’t directly match a category name. Next, they check whether the prediction is relevant. After the LLM makes a prediction, a guardrail compares the meaning of the original query with the predicted category path. This part is done using embeddings, which are numerical representations of text. If the query and the category path get a similarity score that falls below a specific threshold, the system throws away that pairing. To summarize, the three stages have different responsibilities. Historical data is meant to propose candidates. The LLM’s job is to interpret them. And at the end, the guardrail filters irrelevant results. How Instacart Makes The Queries Stronger Even if you have a system that understands a query well enough, the original words that make up the query may retrieve very few useful results. This is where query rewriting helps. Query rewriting generates alternative phrases that can help the search process find more candidates. The older search system at Instacart did this using patterns found in user sessions. But it covered only about 50% of the search traffic. The Instacart engineering team initially tried asking an LLM to generate rewrites using a general prompt. But this didn’t work as expected because just asking the LLM to rewrite the query doesn’t tell the LLM what kind of alternative would be useful. For example, let’s say you have the query “1% milk”. Rewriting might change the query to “one percent milk”. While the meaning stays the same, it does very little to help the user find an alternative product. To make things more effective, Instacart separated rewriting into three tasks: First, they use synonym rewrites that try to express the same request using different wording. “One percent milk” illustrates this relationship. Next, you have broader rewrites that attempt to get rid of some specificity. For example, “milk” can be a broader rewrite of “1% milk” Last, you have substitute rewrites that suggest a different product that might be a good alternative. For example, something like “2% milk” can act as a potential substitute. You might think that these differences are pretty minute, but they change the search approach in different ways. When you broaden a query, you make the constraints less rigid. Making the suggestion of a substitute product changes the requested product. A synonym keeps the intended meaning intact. Each type of rewrite gets a dedicated prompt with specific instructions and examples. They also give it reasoning guidance. Instacart then applies a bunch of post-processing checks and semantic filters. This approach increased rewrite coverage to over 95%, with more than 90% precision across all three types.
