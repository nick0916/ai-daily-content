## Agents write 99% of my code. Here is what I still do.

作者把工作切成「定義、實作、驗收」三段，實作交給 agent，自己把力氣放在前後兩端。

**Why** 作者認為定義與判斷對結果的影響比模型本身更大；他以 2025 年 11 月 Opus 4.5 發布為轉折點，從此幻覺幾乎看不到。

**How** 用 OpenSpec 寫 Markdown spec 讓 Claude 依現有程式碼出計畫，修正幾輪後再實作，並把計畫交給另一個模型審查（模型訓練不同，盲點不同）；bug 先寫失敗測試；完成後用全新 session 審查，自己只看關鍵 diff 並實際操作 app。

**What** Milan 稱 agent 寫了他 99% 的程式碼，Claude Code 占 80%、Codex 占 20%。他公開 63 行的 AGENTS.md，並引用 ETH Zurich 研究：規則檔未提升成功率、成本卻增加 20% 以上，所以刻意保持精簡。另分享六個可複製的 prompt：先出計畫、有疑問就問、用第二個模型、新 session 審查、要求證據、再做一次檢查。

### 重點
- 工作流：定義（一句話需求、對象、限制、驗證方式）→ agent 實作 → 全新 session 審查；每個功能先寫失敗測試、覆蓋率 80%+，計畫由第二個模型審查
- AGENTS.md 刻意只有 63 行、不放 repo 概覽：ETH Zurich 研究發現規則檔未提升成功率、成本卻增加 20% 以上；另一研究指出規則與程式碼不一致時 agent 有 90% 依循舊檔，因此要求 agent 跟隨現有程式碼結構
- 自我修正規則：每次糾正錯誤，agent 就提議新增一條規則（作者決定是否納入）；重大變更仍親自檢查，並加腳本與綠燈 run 納入 definition of done
