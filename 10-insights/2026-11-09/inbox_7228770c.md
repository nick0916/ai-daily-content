## What's up Python? We are living interesting times for sure...

**Why** 作者提醒近期 eMudhra 憑證醜聞與 AI 輔助滲透測試帶來大量紅色警報，需要大範圍更新。

**How** 作者的作法是把 OS、伺服器與所有碰到憑證的 Python 套件（requests、httpx、aiohttp、uv、poetry、pip、certifi 等）連同 Python 本身一併升級。

You need to update a lot of things # Now, I’m not saying you should migrate to Python 3.15. In fact, if you have been following the blog for a while, you have already heard me say that one should stay a version behind stable. So if anything, it’s time to migrate to 3.14. I’m talking about the aftermath of the eMudhra certificate scandal . In short, eMudhra is an Indian certificate authority (the stuff that makes HTTPS secure) that was trusted by pretty much the entire world and yet turned out to have hilariously insecure cryptographic keys, one of them being literally the number 4. It revealed that the entire planet was wide open to MITM attacks, and so everyone needs to update their certificate stores furiously. This means updating your OS, your servers with the latest patch, and all your Python dependencies that touch a certificate: HTTP libs (requests, httpx, aiohttp, etc), package managers (uv, poetry, pip...) and their related tooling (venv, virtualenv, virtualenvwrapper...) as well as all certificate wheels (certifi, py-cert-store, etc). Honestly, I just bumped pretty much everything, including Python itself, on all public-facing projects because the devil is in the details and I don’t want to bother with the granularity. I strongly suggest you do the same. Certificates are, of course, not limited to Python, so do the same for all your tech stacks, and you OS. In fact, thanks to AI pentesting , we have an avalanche of red alerts these days for any single piece of code out there. The Linux IP stack and PHP had a zero-day that required urgent mitigation and patching. A client asked me to work on a Next.js project last week, I put the VM online, and it got pwned in 10 seconds, with an immediate credential extraction. Turns out they had an old version of Node that was vulnerable to injection through multipart forms. Keep your eyes open and your fingers nimble, because it’s the far west out there. Cloudflare Python Workers are generally available # Cloudflare Workers are a weird tech. It’s basically Python web hosting with a request/response model, but with unusual limitations: It runs on Pyodide and in Cloudflare’s proprietary V8 isolates (basically their own flavor of Node VM), so only a limited subset of Python libs are available. It doesn’t persist anything, like the called serverless technologies (think Lambda), so each code run is stateless and doesn’t know about the previous one nor the next. Requests are each limited to 10 ms of CPU time (not wall time, so I/O is NOT counted in those 10ms, you can wait on it up to 30s). A single isolate (so the VM) cannot eat more than 128Mb of RAM for free, exceed that and you get killed. If you run Pyodide and load pandas, that’s a big chunk of budget right there. They are also limited to 6 outbound connections. Your crawlers better behave. You get 100 max workers on their free offer. Honestly, I tried it, and it’s pretty slow. (and sure, all those limits are increased on paid plans) And yet, it has surprisingly good capabilities: It can run FastAPI, Django, and Flask. It has access to the full Cloudflare ecosystem: KV, D1, R2, Durable Objects, Queues, Workflows, Workers AI, Vectorize and Hyperdrive, exposed as plain Python objects on the environment binding. Which means databases and queues with very generous free tiers: 100K key/value read a day, 1K writes, 5M reads a day on sqlite/199K write, 10GB on their S3-compatible object store. That’s not bad. Static files can be up to 25 MB, and you get 20000 files budget as a gift. You could create a FUSE driver to get a free Dropbox on that thing. You get 100,000 requests a day, for free, and egress is not metered. You get CRON and alarms you can set down to 15 minutes. So you are in this weird zone where you need to wrap your architecture around exotic limitations, but in exchange, you get access to dirt-cheap compute in Python. Of course, OVH still has an offer for a full VPS for less than 5 euros a month with 2 cores, 4GB of RAM, 40GB of SSD and unmetered bandwidth , so I would still always choose that over Cloudflare Workers. And of course, PythonAnywhere is still by far the best option for beginners who just want to put their first little Python website online. But if you want some free compute to do some crawling, call some API, have some script running every now and then to check on some data, this is a strange but appealing alternative. Memory Snapshots for CPython # One of the reasons Cloudflare Workers are usable at all is that they snapshot their VM, meaning they save its initialization state so that next time they start it, it doesn’t have to do the entire bootstrapping work all over again. This is a hard requirement, otherwise we would get back to the performance of good old CGI from the 90’. They can do that (I assume) because V8, the Node.js engine, implements this feature, and their isolates (their unit of workers) use V8, even for Python (which, remember, uses Pyodide, so WASM). Python itself doesn’t have such snapshotting capabilities, or rather, CPython doesn’t. Initiatives like Monty do, but they have to make a bunch of compromises to achieve that. Indeed, Python is a language full of side effects, lists are mutable, dict keys are seeded with a random number, and modules can and are dynamically loaded in a number of ways, including now, with lazy loading. So keeping the state of a Python interpreter between two runs is not really easy, and it’s in fact why functions like reload() in IPython work until they don’t and why it’s generally advised not to use them. Nevertheless, during the latest language submit, snapshotting was put on the table as a way to speed up the Python startup by Robert Hood Chatham, a Pyodide maintainer working at... Cloudflare. In preliminary tests, he has shown that Pyodide execution for a simple “Hello, world” program was around 4 times faster (0.353s vs 1.406 s) when loading the interpreter from a memory snapshot vs without. And he wants to bring that to CPython. It’s just the begining of talks on the subject, since, as I mentioned, there are tons of barriers in CPython design that can make that very, very difficult. Yet Monty has shown that such a feature opens the door to a ton of interesting stuff, like pausing and restoring a complicated workload or serializing a full interpreter state to send it somewhere else. It’s interesting stuff, and well beyond performance. PEP 827: Type Manipulation # One of the wonderful things about type declaration in Python is that they are available at runtime. This means you can read type information from Python itself. It is not the case in most languages, and it’s what allows wonderful stuff like Pydantic and FastAPI to be so nice. But while you can read the types from Python, and you can even sometimes programmatically change very simple types (like containers typed with generics) based on a condition, you cannot generate types on the fly. At least not in a way that allows type checkers to keep working. Type checkers assume the types are defined statically, you can’t create a list of types in a loop, for example. Now, why the hell would you want to do such black magic? Well, imagine a library that does a query (to a database, a Web API, anything external that requires params). Depending on what you pass as arguments, you get different results. Right now, we can’t type that in Python. There is no way to say “if we ask for a name, the type is string, but if we ask for an age, the type is int”. PEP 827 is a proposal to change that: create a way to be able to generate typing information depending on the situation. Let’s be honest, it’s obscure, complicated, and ugly, with things like: ternary operations on types: true_type if bool_type else false_type comprehension on types: *[t for t in Iter[iter_t]] and type introspection: typing.Members[t] would return an iterable of the type’s attributes. But it’s also super useful. If you have ever worked with a language (like TypeScript or C#) that can tell you that your return value from a DB is correctly processed, you’ll know it’s empowering. Here is what it could look like (this doesn’t exist yet, I’m making this up). Let’s say you query an API that can return animals, for now either dogs or chickens. Here is the client code, which is the part a library author would write: from dataclasses import dataclass
from typing import Literal, Never
from imaginary_animal_lib import make_animal

@dataclass
class Dog:
 name: str
 # A dog child is a dog
 def get_child(self) -> Dog:
 return Dog(name=f"pup of {self.name}")

@dataclass
class Egg:
 laid_at: str

@dataclass
class Chicken:
 name: str
 # But a chicken child is an egg!
 def get_child(self) -> Egg:
 return Egg(laid_at="2026-11-08")

# We create a type that says "if the type requested is the string dog,
# this will return a dog, but if we request a chicken, this will return a chicken type"
type DynamicAnimalType[K] = (
 Dog if K is Literal["dog"]
 else Chicken if K is Literal["chicken"]
)

type AnimalType = Literal["dog", "chicken"]

class Client:
 # We now setup the K placeholder as the variable that will define
 # the type (chicken or dog) that is returned
 def get_animal[K: AnimalType](self, kind: K) -> DynamicAnimalType[K]:
 return make_animal(kind, self._http.get(f"/animals/{kind}").json()) Copy And now here is how you would use the client, which is the part most people would write: dog = client.get_animal("dog") # this does an HTTP request
reveal_type(dog) # Dog
print(dog.get_child().name) # OK — child is a Dog, so it has .name

chicken = client.get_animal("chicken")
reveal_type(chicken) # Chicken
egg = chicken.get_child()
reveal_type(egg) # Egg
print(egg.name) # type error: your type check can catch this! Copy As usual with Python types, this complexity is completely optional. I’m not expecting most devs to use this, or even know about it. But library authors would have the ability to provide types for queries. Django would be able to let your type checker know your ORM query is correctly processed. These kinds of things, in an AI world, are going to be very useful as guardrails, and I think pros outweigh the cons. I don’t know if this will be the final form of this proposal, in fact, I doubt it. But Yury Selivanov (the core dev behind uvloop) is on the list of authors, so it gives me confidence.
