## How LinkedIn Uses AI to Review 40,000 Pull Requests a Week

LinkedIn 用多個 AI agent 互相驗證的方式自動審查 PR，讓人類審查者只需處理已過濾的意見。

**Why** 程式碼代理讓寫程式變快，瓶頸轉移到 code review；廠商託管的 reviewer 留言雜訊多且太通用，工程師因此要求退出。單一模型自建則有幻覺與知識盲區，甚至出現行號對不上 diff 的留言。

**How** 採 orchestrator-subagent 架構：多個 subagent（常用不同模型）獨立審查同一份 PR 並回報帶行號的發現，orchestrator 合併重疊結果、依信心排序，只發布可靠意見；規則分三層（公司層 YAML、repo 層 markdown、PR 類型層），由專用 subagent 套用。

**What** LinkedIn 內部 reviewer 每週涵蓋超過 4 萬個 PR，多數審查在第一位人類審查者開啟 PR 前就已發布；公司有超過 1 萬個活躍 repo，採部分自動化（AI 先審、人類保有核准權）。原文（已被截斷）還涵蓋評估方式與新瓶頸的走向。

### 重點
- 規模：LinkedIn 超過 1 萬個活躍 repo，內部 AI reviewer 每週涵蓋 4 萬+ PR，多數審查早於首位人類審查者
- 三種路線的取捨：廠商託管（雜訊多、無法控管更新）→ 單一現成模型加自訂規則（幻覺、知識盲區）→ 自建多 agent（互相驗證、不同模型補盲區）
- 三層規則設計：公司層 YAML、repo 層 markdown、PR 類型層，各有範圍與負責人；好的 AI 審查意見需具備 grounded、high-signal、codebase-aware、timely 四項特性

Software development has two main steps. An engineer writes a change, and other engineers review it before it merges into the main codebase. Software development’s two main steps When an engineer writes the code, the change becomes a PR. Then reviewers read its diff, that is, the lines it adds, removes, or changes. Here are the typical steps from when a writer opens a PR to when the PR is merged back into the codebase: The author opens a PR from a branch that has the change. The code host, such as GitHub, notifies the reviewers and starts continuous integration (CI), which runs tests and linters (to flag style problems and simple errors). A reviewer reads the PR and comments on specific lines. The author pushes fixes. Then the reviewer looks again. The reviewer approves, and the PR merges. The typical path of a PR, from opening to merging. AI is changing this development process, because it can now help with some of these steps. Engineers hand those steps to AI agents and spend more of their time focusing on intent and judgement. That is AI-native development. Specifically for the writing step, frontier coding agents have shown promise lately. Given a task, an agent implements the feature, writes the tests, then runs those tests, and iterates until they pass. Finally, it opens a PR for review. Coding agents automate writing, but PRs still waits for review. With coding agents, writing (the first step) can now be largely automated and done much faster. Instead of an engineer spending hours or days writing a change, the agent spends minutes writing it. But if real humans still have to review the proposed changes, the process will still be slow, because engineers’ hours are still fixed and limited. Writing got faster, so review became the bottleneck. The fix is a system that can reliably review code, ideally before humans do. That system is called an AI reviewer. It reads a PR the way a human reviewer would and comments on the lines that need attention. Once the automated code review is complete, the author, in this case the coding agent, addresses them so human reviewers spend their limited time on judging the fixes. Since models are also getting better at reading code, more teams are automating reviews this way [2]. They mostly differ in the extent to which they aim to automate the reviewing process. Full automation would let AI approve changes on its own. This is difficult, and most labs are not there yet. Partial automation keeps human approval on changes and gives AI the first pass. This makes the process faster but keeps real humans in the loop to reduce the risk of merging buggy or insecure code. Partial automation is more feasible these days, and companies that have an AI reviewer in place, like LinkedIn, usually use partial automation. In the rest of this article, we focus on partial automation. Full vs partial automation But why is building an AI reviewer challenging? For an AI reviewer to be reliable, it has to have four properties: Grounded: it flags real problems in the changed lines. High-signal: the issues it produces are real bugs and high-risk lines (not just minor style nits a linter would catch). Codebase-aware: it follows the codebase’s own conventions. Timely: it comments while the author can still act on it. The four properties an AI review comment needs Getting all four at once is the hard part. PRs still get a human review, but the AI review comes first. As a company, you have different options to have an AI reviewer in place. Some options are easier to set up but less flexible, while others take more work to build but give you more control over the quality of the comments. Three common directions are: Use a vendor’s reviewer Use an off-the-shelf model with your rules Build a custom multi-agent review system Three ways to get an AI reviewer Direction 1: Use a vendor’s reviewer A fast way to have an AI reviewer in place is to simply buy a hosted system from a vendor. The reviewer connects to the code host and comments on each new PR moving forward. So you don’t have to build the system internally. This direction is simple to set up, does not need any particular expertise, and is probably the fastest option. But it has two major limits. First, it is generic. You can add a rule file, but the vendor controls the prompts and the harness, so many comments are generic and could apply to any project. The second limit is control. The vendor owns the system, so it decides when the model or the instructions change. You cannot test an update before engineers see it or gradually roll out a change. A vendor’s reviewer meets your codebase only through a rules file. LinkedIn tried this option first. During an AI-native pilot, teams were asked to opt in to a vendor’s hosted reviewer. But the team observed that the comments were noisy and generic. They did not fit LinkedIn’s codebase and each repository’s rules. When the comments are noisy, engineers lose trust. Soon, engineers asked to opt out, which meant the full manual review was back again. The team also had no control over the vendor’s changes. Min put it this way: “You don’t own anything. They do something, they change something, you just react to it.” Direction 2: Use an off-the-shelf model with your rules Since a hosted reviewer is too generic, a natural next step is to use an off-the-shelf model, but build your own harness around it. That way, you can choose your own prompts and write the codebase’s own rules into its instructions. With those instructions and more control over the harness, the comments will be more specific to your conventions. This direction sounds promising: the comments would be specific to the codebase and would likely arrive quickly, before human review. But it has two main problems. The first problem is hallucination. Because the system relies on a single model and there is no verification in place, if the model hallucinates, nothing will catch it. The author will end up with a comment about a problem that does not exist, or a real problem attached to the wrong line. Grounded vs. hallucinated comment The second problem is knowledge gaps. A model learns what good and bad code look like from its training data. With a single model, it will work well on areas that overlap with its training data, but will fail on out-of-distribution inputs or inputs that were less frequent in the training data. That means a single reviewer model misses the same classes of issues repeatedly and may over-flag the same low-value issues. A single model works well on what looks like its training data. LinkedIn also observed the same issues when the team built the review system with their repository-specific rules. The model gave good results but produced many hallucinations, and some of its comments did not even match the line numbers in the diff. Using a different model for review than for writing code did not fix the hallucination issue. But that idea led the team to ask whether a second model could check and verify the first model, the idea behind the multi-agent design. Direction 3: Build a custom multi-agent review system This direction relies on multiple agents to produce grounded reviews. There are different design patterns for multi-agent systems, but a popular one is the orchestrator-subagent pattern [3], where one agent hands work to several subagents and combines their results. For code review, the subagents independently review the same PR, often each with a different model, and return their findings with line numbers. The orchestrator then merges overlapping findings, ranks them by confidence, and posts only reliable reviews. The orchestrator-subagent pattern This design can mitigate most of the limitations of the previous directions because you own the whole system, different models cover each other’s knowledge gaps, and findings by different agents must be verified by others to survive and be posted. To add your rules and codebase conventions, there are two ways. One is context injection, which means adding a rule file to the repository that the AI reviewer reads on every PR. This can work in simple codebases, but is not a flexible approach because some rules apply to every repository, some to one repository, and some to one kind of change. A single file being injected as context cannot contain all three or combine the right ones for each PR. The other approach, which LinkedIn used, is a layered design. You design several tiers, and each has its own scope, owner, and rules. Then a dedicated subagent uses those rules to perform an independent review. LinkedIn used the following three tiers: Company-wide rules apply to every repository. These can be YAML files clarifying what the model should check. Repository rules cover one codebase. This can be a markdown file containing the team’s conventions like coding standards and review criteria. Pull request rules apply only to one kind of change. Layered rules to get a right mix of company, team, and change-specific checks. To better understand how this system reviews a PR, let’s go over a concrete example and see how each step handles it.
