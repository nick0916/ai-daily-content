## Software correctness & supply chain security, with Sean Allen

訪談一位專注軟體正確性的工程師，談如何讓錯誤在寫程式與編譯階段就被擋下，而不是靠事後測試。

**Why** 受訪者 Sean Allen（Antithesis distinguished engineer、Pony 語言核心貢獻者）認為多數人一開始並不知道軟體「正確」該長什麼樣，只知道壞掉時的樣子。

**How** 用 ML 家族語言（如 OCaml、Rust）的 sum type 加 exhaustive matching，新增一種 case 時編譯器會列出所有漏處理的地方；再搭配「讓非法狀態無法被表達」的型別設計，以及用可重複執行的 workload（如 Bank Test）取代單純 unit test。

**What** 文章（含 YouTube 版）涵蓋正確性導向的語言、對測試的批判、品質不是事後 gate、tech debt 不一定要還、供應鏈攻擊沒有單一解法、Pony 的可預測 GC，以及「先慢設計才能後快」。內文後半被截斷，以上僅依可見段落整理。

### 重點
- ML 家族語言的 sum type 加 exhaustive matching，把「忘了處理新 case」變成編譯錯誤；Rust 的 sum type 與 pattern matching 即來自 ML
- 主張「make illegal states unrepresentable」：先用型別限制允許的狀態與轉換，手動測試是最晚、最差的驗證方式
- 以 workload（例如 The Bank Test 壓測資料庫 isolation）重複執行，比 example-based unit test 更穩健；TDD kata 中隨機化輸入即進入 property-based testing

A sum type says ‘this value could be one of these things’, a bit like enumerations in Java. You combine that with pattern matching, and then with exhaustive matching. Say I have a sum type, which could be five different things. Instead of an if statement , I pattern match for which one it is. In other words, exhaustive matching turns every “forgot to handle the new case” bug into a compilation error. It is a gloriously wonderful experience to work with such a language.” 2. Does anybody care about testing? You’ve written “no one cares about testing. I don’t value tests,” but it’s odd to hear this from you as someone who does care about correctness. Sean: “I wrote that because people think of Antithesis as a testing company, and I don’t think of it that way. I think of it as a software verification and correctness company – which is very different. Tests are things that you do to verify that things are working , for things you have no better way to verify. The worst type of testing is manual testing. You can automate it, and get more and more sophisticated with automated tests, but you are still doing something at the late stage of development. You should do as much as possible before you get to testing. With ML languages, you can usually represent within the type system what the states are, and what the allowable transitions are. Once you have these in place, you can make sure that things can never transition to a state you don’t expect. Being able to do so is huge! In practice, when you’re trying to work out whether your system works, you’re not thinking about the entire thing all the way down. You’re only thinking about the stuff your type system will not allow you to express.
