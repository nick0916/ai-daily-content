## Your Team's Agents Are All Shipping to the Same Code at Once - Patrick Debois, Tessl

當多人與多個 agent 同時對同一份程式碼出貨，要從「持續交付」改成「並行交付」。

**Why** 啟用多人 software factory 後 PR 量可增加約 10 倍，agent 彼此衝突、每次 merge 後其他 PR 要 rebase 重跑測試，CI/CD 變慢變貴，人也來不及審與跟上變更。

**How** 事前把工作依模組/AST 拆分、agent 認領 ticket 並宣告要改的檔案、用 worktree 等隔離環境；衝突時等待、重試或重新協商計畫，merge 改以函式層級與「意圖」檢查，並用 speculative merge train 先成對檢查相容性；人的部分則讓 agent 加入團隊聊天補完 ticket、以選項式問題減少決策負擔、把決策記入共享帳本，並依風險決定審查深度。

**What** Tessl 的 Patrick Debois 在 AI Engineer 的演講；例子是一個 PR 把發票總額改成美分、另一個 PR 的報表需要原單位，程式碼不衝突但意圖衝突。他還提到 Helix ML 讓人在 agent 卡住時帶著完整 context 跳進 IDE 再交還，以及組成類似 platform team 的「factory team」，並在 concurrent.cd 整理相關研究。

### 重點
- 並行交付手法：事前拆工作、agent 認領 ticket 並宣告將改動的檔案、worktree/資料庫快照/數位孿生隔離環境；衝突時等待、重試或重新協商計畫
- 意圖衝突範例：一個 PR 把發票金額改成美分、另一個 PR 的報表仍預期原單位，程式碼可合併、測試通過但語意不一致；speculative merge train 先成對檢查相容 PR 以減少 rebase
- 人機協作：agent 加入團隊聊天精煉 ticket、用選項式提問、決策寫入共享 ledger，審查依風險分級（文件類可放行、認證類需人審），並成立 factory team 維護 skills 與 context
