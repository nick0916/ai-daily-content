## Rethinking Claude Code Best Practices — Lydia Hallie, Anthropic

模型變強後，人從逐步審核退到只負責開頭和驗收，原本由人做的事要交給模型、harness 和執行環境。

**Why** Anthropic 內部每天的變更數從 5 月約 2,500 增加到 9 月超過 30,000，人同時管數十個跑數小時的 session，不可能再逐步盯著、逐個核准。

**How** 把原本人做的事分給三層：模型負責 steering（用 auto mode 取代手動核准）、harness 用 deny rule、hooks 與 CI 把關，環境用 sandbox 或雲端 session 限制副作用；最後再由 orchestrator session 自動開子 session 並驗收結果。

**What** Lydia Hallie（Claude Code 團隊）在 AI Engineer 的演講，以 Opus 55 與 Fable 52 為例，重點如下：CLAUDE.md 只留 Claude 從程式碼看不到的資訊，可用 doctor prompt audit 檢查；Anthropic 研究中真人只攔下約 14% 危險指令，auto mode 攔下 89%；deny rule 在 classifier 之前檢查，不可逆操作（讀 .env、丟棄未 commit 變更）仍應設成規則；hook 腳本用 exit code 2（而非 1）才會讓 Claude 回頭修正；CI autofix、merge when ready 與 Claude 先審 PR 是最後防線；Claude Code projects（beta）用 Fable 當 orchestrator、Opus 55 當執行 threads。

### 重點
- 安全數據：Anthropic 研究中真人只抓到約 14% 的明確危險指令，auto mode 擋下 89%；要保證不發生只能靠 harness 的 deny rule，且 deny rule 先於 classifier 檢查
- 判斷準則：Claude 做錯一次能否收回？能（改錯程式碼可 revert）就交給模型；不能（丟棄未 commit 變更、讀到 key 進 transcript）就設 deny rule；npm test 這類腳本的副作用要靠 sandbox 或雲端 session 限制
- 驗證技巧：在 prompt 定義 done 並要求拆成各自有測試的任務；必須執行的檢查用 hooks（編輯後跑 linter、完成任務跑相關測試、結束時跑全套測試），腳本失敗須 exit code 2 才會送回修正；再搭配 CI autofix、merge when ready，並依風險決定審核人數
