## How Anthropic Redesigned Source Control

Anthropic 發現 AI 寫程式的速度已經超過 Git 工作流能承受的量，所以自建了以伺服器為中心的版本控制系統 Scion。

**Why** Claude 產生的程式碼暴增，下載 repo、準備工作區、記錄變更成為瓶頸；merged changes 從 2026 年 5 月約每天 2500 筆增至 9 月超過 30000 筆。

**How** Scion 讓伺服器負責 blame、diff、commit、merge、rebase 等 repo 操作，client（scn）只保留有限快取並準備檔案；變更以 changeset 記錄，metadata 存 Spanner，壓縮後的檔案內容放雲端物件儲存；物件以內容定址，可被共用快取。

**What** 依文章數據，main 分支歷史接近 100 GB，壓縮後工作副本超過 25 GB，CI 每天約 2500 萬次 checkout；若每次 checkout 都傳完整壓縮工作副本，一天可能產生超過 600 PB 流量。Git 方案（shallow clone、sparse checkout、repo seed、數百個內部 mirror）因 mirror 同步與 seed 過期而難以維持。代價是對服務可用性與連線的高度依賴。

### 重點
- 規模數據：merged changes 由約 2500/天（2026 年 5 月）增至 30000+/天（9 月）；CI 約 2500 萬次 checkout/天；naive 傳輸會產生 600 PB+/天流量
- Git 的本地獨立性對永遠在線的 agent 與 CI 沒有價值；Anthropic 最高峰運行數百個內部 mirror，同步與 seed 過期成為負擔
- Scion 設計：client-server 不對稱（伺服器做 repo 操作、無 push 步驟）、changeset 記錄相對第一個 parent 的檔案變更、內容定址的不可變物件配合階層式快取

References at the end. Please comment if you notice any inaccuracies. How Source Control Works As you will already know, a software project is made up of files that change continuously. Developers add features. They correct mistakes and update dependencies. They also sometimes need to recover an earlier version. A source control system records all these changes and lets multiple developers work on the same codebase. Let’s look at a few key terms related to source control. A repository contains the project’s versioned information. Next, you have a commit that denotes a specific version along with other details such as the author, a description, and a history of the earlier commits. A branch is used to demarcate a line of development. For example, your main branch signifies the line of code into which you integrate all the reviewed and approved changes. Different developers can work on different branches and combine their code through a merge process. The files present on a developer’s machine are known as the working copy. A checkout process prepares those files for a specific version. Lastly, you also have automated systems that rely on source control. Continuous integration (CI) runs processes such as compilation, testing, and other checks when code changes. Each job may need a workspace that contains the appropriate version of the code. Coding agents and research jobs need similar environments. Anthropic’s Problem with Source Control Anthropic stores a large amount of its code in a monorepo. You can think of a monorepo as a shared repository that contains multiple projects and components. This way, code that is related can share a common history. But it also means that many separate activities might depend on the same source control infrastructure. But a large repository is only a part of the story. Anthropic’s problem is much deeper. They report that merged changes have grown from roughly 2500 per day in May 2026 to more than 30000 per day by September. Meanwhile, the size of its main branch’s history is close to 100 GB. Even a compressed working copy goes beyond 25 GB. Source: Anthropic Research The CI system is doing approximately 25 million checkouts per day. This number is before counting developer environments, agent sandboxes, and research jobs. To be clear, you shouldn’t think of these checkouts as individual code changes. A single change can spawn many jobs. And each job prepares an environment for doing its work. Ultimately, your infrastructure workload can get much larger than the number of changes being merged. Source: Anthropic Research For example, a naive approach to transfer a compressed working copy for every CI checkout can generate more than 600 PB of traffic per day. Therefore, the practical problem Anthropic faces has two sides. One is that the system must be able to accept new changes quickly. Second, it must be able to distribute the code to a huge number of consumers. If you improve only one aspect, the other can become a bottleneck. Why Git Couldn’t Solve the Problem The local independence of Git becomes quite expensive in this type of workload. As you might know, Git is designed in a way that an ordinary full clone of the codebase can be used as a self-contained repository. When the necessary data is locally available, you can use Git to inspect history, compare versions, and create commits without the need to contact a central service. This is a great strength of Git. However, Anthropic’s workload is such that this independence is not valuable. Most of the clients are automated jobs and agents that already depend on network services. At the same time, if you give those clients a good chunk of repository data, it leads to repeated transfer, storage, and maintenance costs. To be clear, Git also has ways to reduce those costs. Anthropic used a bunch of these strategies. For example, they use features like shallow clones, sparse checkouts, partial clones, internal mirrors, and repository seeds. Each of these techniques can handle different parts of the problem. For example, a feature like sparse checkout helps deal with files that are part of the workspace. The first architecture Anthropic built was around the use of Git. You had jobs start from seeds, obtain additional data through caches, and use layers of repository mirrors. At its peak, the Anthropic engineering team was operating several hundred internal mirrors to distribute traffic. But they had to keep all these mirrors in sync with each other as the repository data changed. Seeds also became outdated as the rate of merging increased. Operations that needed historical data became a lot harder to manage because clients held only partial repository data. The Anthropic team realized that its workflow already had one authoritative shared repository while the infrastructure supported a lot of independence at the client level. With Scion, they changed this responsibility allocation approach. How Scion Works Scion makes the server responsible for repository operations. It assumes that clients can reach a source control service when they need data. In this setup, the server answers historical data queries, calculates diffs, and creates commits. It also performs merges and rebases. The client (known as scn) maintains a limited cache and prepares files on disk. It watches for local filesystem changes and provides an interface for developers and jobs to deal with the service. This setup is known as the client-server asymmetry. You can think of it as the client and server having different capabilities and responsibilities. For example, let’s say you have a tool that needs to find out the change behind a particular line of code. This operation is commonly known as blame. In Scion’s operating model, the tool asks the service for the answer to its question. It doesn’t need to assemble enough local history to calculate the answer. The same principle applies when you’ve to create changes. In Git, you have a commit that’s created locally and later shared through a push. In Scion, you create a commit using a server operation. There’s no separate push step. You might think that such a centralized service uses a single server that contains everything. But that’s not the case. Anthropic distributes the data and scales the service across machines. There’s no fully materialized repository on any single individual server. The tradeoff is that you have a strong dependence on service availability and connectivity. How Changes are Handled by Scion Changesets provide a small, durable record of each change. Once you create a commit on the server, you need to ensure that they are accepted efficiently. Scion’s basic unit for managing this is a changeset. You can think of this changeset as a durable record of a change. You can easily construct other useful representations of the repository from this changeset. To understand its structure, two terms are important. First is a blob that stores the contents of the file. Second is a tree that describes the contents of the directory. It connects names to files and subdirectories. In Git, a commit points to a root tree that represents the project at that version. Source: Anthropic Research A Scion changeset records the files that changed relative to its first parent. This happens together with a reference to their contents. For example, let’s say you have a change that updates a file named “docs/guide[dot]md”, deletes “src/legacy[dot]rs, and modifies “tools/build[dot]sh”. The changeset keeps a record of those file changes and their relevant references. It also keeps the parent information and author details. Here, “changed files” doesn’t mean a sequence of line-by-line patches. A merge can also have multiple parents. The first parent gives you the baseline against which Scion records its file changes. Changeset metadata is stored in Spanner, which is a distributed database. Compressed file contents are kept in cloud object storage. The root tree is derived by the server rather than being stored directly inside the changeset. This way, you can record a change based on the changed data and affected structures. No need to process the whole repository. How Scion Caches Data Using immutable objects makes it easy to use shared caching. Scion recognizes its source control objects by their contents. This technique is known as content-addressing. In this approach, you have a hash function that calculates an identifier from the contents of an object. The system can then find that object later using this identifier. If there’s a change in the content, the new object gets a different ID value. This way, your stored objects are immutable. A specific ID continues to refer to the same data. For example, let’s say you have a cache that contains a particular version of “parser[dot].rs”. If you have another job that asks for the same object, the cache can return it without asking another server if the contents have been modified. If there’s a new version of the file, it means the object is different. There are two consequences of this. One is that you can use identical content. Cached historical objects don’t need freshness checks merely because development is happening somewhere else in the repository. Git uses content addressing. But the way Scion differs is in how extensively its service and architecture are organized around asking for and caching these objects. Information still changes in the system. For example, let’s say the name “main” moves as changes are integrated. The immutable object that represents a specific version and the mutable name that identifies the latest version require you to treat things differently.
