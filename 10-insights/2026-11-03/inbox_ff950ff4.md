## How Netflix Uses AI Agents for Performance Engineering

Netflix 讓 AI agent 自動讀效能剖析資料、找出程式瓶頸並提出修正，取代人工看 flame graph。

**Why** 傳統效能優化靠少數專家手動分析，無法規模化；AI 輔助寫碼讓程式產出更快，但 LLM 看不到執行環境，容易產生在大規模下浪費資源的程式。

**How** 不同語言 profiler（async-profiler、py-spy、pprof）都輸出 call stack，可用單一管線處理；讓 LLM 以已知反模式比對實際 call stack，並用 package prefix 規則限定範圍，避免它浪費推理在 GC、kernel syscall 或第三方框架上。修正需先通過單元／整合／契約測試，再走 canary 部署。

**What** 上線後找出四類問題：Java Streams 中 ImmutableMap 的 O(N²) 累積（佔 8.8% CPU）、熱路徑上的 regex（佔 46% CPU，改查表後快 22 倍）、每次呼叫新建 HashSet（佔 47% heap）、每次呼叫查 metric counter（佔 66% CPU，業務邏輯僅 0.3%，且同樣問題出現在三個獨立服務）。

### 重點
- 給 LLM 嚴格的 package prefix 範圍，才能避免它把推理耗在 JVM GC、kernel syscall、第三方框架上
- regex replaceAll 佔 46% CPU，換成預先計算的查表後快 22 倍；Metrics.counter 每次查找佔 66% CPU，改為類別初始化時快取
- 安全機制：先通過既有單元／整合／契約測試，再做 canary 部署，才進 production

First, you trigger profiling for an application. A developer tries to detect high latency or increased resource usage by triggering a profiler on a live production server. Can LLMs Handle Profile Data Netflix wanted to test whether automation could remove these issues. They set up an experiment to find out if an LLM can read and make sense of raw profiling data directly. Different languages have different profilers. But they use a shared language and store the same core information. For example, JVM’s async-profiler or Java Flight Recorder operates at 100 Hz sampling to capture execution traces, memory allocation rates, and thread lock contention. Python’s py-spy provides low-overhead, async stack sampling of live production processes. Go has pprof, which generates goroutine profiles, heap snapshots, and block contention data. Each one of these profilers breaks down execution into call stacks. They track two main metrics. First, you have the inclusive time. This is the total time spent executing a function. It includes every child function and the subroutines called by this function. Second, you have the Self (CPU) Time. It’s the time spent running code purely inside the function itself. No external calls are involved. With this exercise, the Netflix engineering team came to the conclusion that a single analytical pipeline could understand data from almost any programming runtime. Another advantage of LLMs is that they don’t have to guess how an algorithm works from scratch. Since LLMs have been broadly trained on many software repositories, they are mostly familiar with classic programming anti-patterns. For example, they know that quadratic loops where a hot method is called again and again for each item in a collection aren’t a good idea. Also, loop invariants where you compute a calculation for every iteration of the loop instead of making the calculation once at the beginning. Other patterns include excessive object allocation on hot execution paths and “N+1” query patterns. Due to this knowledge base of LLMs, you don’t need to ask an AI model to guess why an application might be performing poorly. You can build a workflow that asks the model to pattern-match known performance bugs against actual call stacks. The Agentic Profiling Pipeline Netflix built an automated performance system that wraps the LLM inside a well-defined pipeline. A key lesson Netflix engineers learnt during this implementation was about scoping. If you feed an LLM a complete, raw stack trace without boundaries, it can get distracted. Often, the model spends a lot of reasoning tokens analyzing internal JVM garbage collection pauses, low-level Linux kernel syscalls, or even 3rd party open-source framework overhead. Application developers don’t have any control over such internal library concerns or OS routines. Therefore, you need to provide the agent with strict package prefix rules. This way, the model can ignore generic platform noise and focus on tracing only the specific application code. The Problems Netflix Found in Production When the Netflix engineering team deployed the profiling pipeline against its production service, the agent found 4 major categories of performance bugs. First was an algorithmic bottleneck that wasted 8.8% of CPU resources. The agent found an aggregation method using Java Streams where an immutable map was updated inside a reduction step. // Anti-pattern: O(N^2) accumulation inside stream reduction

 .build();
}); Since putAll(acc) copies every existing key-value pair on every step, you need to copy elements again and again to build a map of size N. This results in quadratic complexity. stream()
 .flatMap(e -> e.entrySet().stream())
 .collect(toMap(Entry::getKey, Entry::getValue)); The second category was about regular expressions on the hot path. In a service, the developer had to sanitize incoming request strings by modifying characters that weren’t allowed. The earlier implementation ran a raw regular expression substitution on every request. // Anti-pattern: Dynamic regex evaluation per request
String sanitized = input.replaceAll(”[^a-zA-Z0-9.-]”, “_”); As you might know, evaluating regular expressions involves parsing and state-machine transitions. This logic on high-volume traffic used 46% of the service’s CPU time. The agent replaced the regex evaluation with a pre-computed lookup table that checked characters by index. The execution got 22 times faster. The next category was related to unnecessary object allocation that caused OOM crashes. A service frequently checked whether incoming data payloads contained specific metadata fields. To perform the check, the code was creating a new, heavy HashSet on every incoming call. However, the underlying data object already had an internal lookup method available. Also, instantiating millions of such objects consumed 47% of the service’s total heap collections. The agent fixed this issue by removing the redundant object instantiations and modified the code to reuse the cached method. The next category was around library misuse. For example, the discovery involved metric telemetry instrumentation. One of the services tracked operations by looking up a counter from a metric registry on every single call. // Anti-pattern: Looking up metric instances on every function execution
Metrics.counter(”request.count”).increment(); When the query was sent to the registry, it needed dictionary lookups and internal synchronization locks. The profiler showed that the work consumed 66% of the CPU, whereas the actual business logic used only 0.3%. The agent fixed it by caching the metric counter reference at the time of class initialization. Also, it found that the same issue was happening across three independent services.
