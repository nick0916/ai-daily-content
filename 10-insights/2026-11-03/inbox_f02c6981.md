## How software engineering is changing: a tale of two eras

一位工程師從 AI 前時代到 AI 原生新創，每月合併的 PR 增加約十倍，同時瓶頸從寫程式轉移到協作與審查。

**Why** AI 讓寫程式變快後，溝通成本、人工 code review 等舊流程成為瓶頸，團隊文化若不跟著改就無法吃到紅利。

**How** 作者用 Claude Code Desktop 同時跑 3-5 個任務、讓 agent 跑 1-2 小時產出 PR，並用 Claude Code GitHub Actions 建立 code review agent 取代人工審查；一人負責整個功能的前後端與設計。

**What** 這是 Pragmatic Engineer 五週年徵文比賽（125 篇投稿）的 $10,000 首獎文章，作者為 Neil Kakkar。他在 Tano 每月 200+ PR，約為 PostHog 時期（每月 8-20 個）的 11 倍，PostHog 又是 Bloomberg 的 2.4 倍。取捨是快速出貨並接受事後修補，例如 agent 生成的幣別程式碼假設所有貨幣最小單位都是 100（巴林第納爾是 1,000 fulūs），且沒用既有的幣別工具函式；新限制包括 context switching、失去共享脈絡、較少設計思考與 AI 用量上限。

### 重點
- Neil Kakkar 每月合併 PR 從 Bloomberg/PostHog 時期的 8-20 個增至 Tano 的 200+ 個（約 11 倍），且若只有自己用 AI、其他人仍要 review，估計僅有 1-2 倍增益（作者推論）
- Tano 的 PR 預設只由 Claude Code GitHub Actions 的 review agent 審查，另有高風險變更時可手動啟動的更強 agent；新人約 3-8 週後取得免人工審查資格
- Agent 單次跑完一個完整功能需 1-2 小時，並用每個 PR 自動產生的 HTML 摘要來快速檢視；代價是出現如幣別最小單位誤判這類錯誤

Old constraints that disappeared Eleven times more PRs per month at Tano wouldn’t be possible without AI; I couldn’t write 100k+ lines of code a month by hand, let alone think through that many things. Furthermore, distractions during a normal work day – like new bugs, small feature requests, emergency incidents – break flow and decrease productivity. With AI, these can be passed onto a parallel work thread and not take up focus, front and centre. How much does the 11x multiplier stack because of everything else, apart from AI? Imagine visiting a pre-AI PostHog where reviews are mandatory as a time traveller from 2026, and you’re the only engineer there with secret access to AI tech from the future. At best, I think you’ll hit a 1-2x productivity gain because the bottleneck shifts from writing to PR approvals – but only for you . Others still aren’t free to review your completed PRs, and your PR output being much faster makes the review queue longer. At Tano where we’re shipping 10x more, bottlenecks like this and others appear, like communicating with colleagues about what you’re doing, reviewing code, and figuring out what to build next. Let’s talk about some of these. Communication overhead: How engineering works together Engineers at Tano work as independently as possible. We come together and talk through big architecture decisions that affect the whole product, but for most things, there’s enough trust at the company that I can go do what I think is best. They also trust that if I’m not sure about what to do, or if there’s risks involved, that I’ll flag the risks and account for trade-offs. A big part of moving fast is having just one person responsible for things. Of course, this assumes that they can figure out how to do it themselves, and go ship it. At PostHog, when building out surveys, two engineers and one designer worked together to ship V1 in a month. All three of us iterated on the design, backend, and frontend. When I discovered something that needed to change on the backend, it often meant the other engineer needed to change something on the frontend as well. This was the communication overhead. Even so, engineers who worked together went faster than I would, figuring out the backend, then building out the frontend, and then iterating over any new constraints. Now that writing code is faster, a communication overhead makes little sense. If I imagine that we’d be building the same survey functionality today, it’s now a lot more efficient if one person owns the entire stack end-to-end; design, frontend, backend. With Claude Code, this is doable by one engineer. There’s still value in talking about unknown unknowns and things I’m not sure about with other engineers, but where the output is mostly known and it’s a straightforward feature or product, then I think one person working solo is more effective. Code reviews Code reviews are optional at Tano. That is, they are optional once you have a handle on the codebase. I felt comfortable enough three weeks after I started, but depending on experience it varies, going up to eight weeks.
