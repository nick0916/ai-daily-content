## From Solving Netflix’s Data Lake Problems to Becoming the Dominant Open Table Format: The Evolution of Apache Iceberg

說明 Apache Iceberg 如何從 Netflix 內部為了解決 Hive 資料湖問題的方案，演變成主流開放表格式。 **Why** Netflix 原本用 Hive，但 Hive 為 HDFS 設計，檔案系統沒有交易語意，需靠 Metastore 鎖定寫入；讀取前必須列出檔案，Netflix 曾為 query planning 等超過 9 分鐘；搬到物件儲存後，同一 partition 的資料集中在相同 prefix，吞吐量受限。 **How** Iceberg 以樂觀並行控制（OCC）取代鎖，每位寫入者建立自己的 snapshot、變更後再 commit，衝突時中止；並用 snapshot 明確追蹤每個檔案以略過 file listing，且 snapshot metadata 採分層設計，避免每次都重寫數百萬筆檔案清單。 **What** 文章（Vu Trinh）回顧 Iceberg 自 2017 年起由 Ryan Blue 領導的團隊在 Netflix 開發，到 2026 年成為最常用的開放表格式之一；Google、Microsoft、AWS、Snowflake 乃至 Delta Lake 的創造者 Databricks 都在 lakehouse 產品中支援。原文節錄僅涵蓋早期背景與設計動機，後續演進內容被付費牆截斷。

### 重點
- Hive 三大問題：檔案系統無交易語意需靠 Metastore 鎖、讀取前必須 file listing（Netflix 曾 query planning 等超過 9 分鐘）、物件儲存上同 partition 共用 prefix 限制吞吐
- Iceberg 以 OCC + snapshot isolation 取代鎖：寫入者建立自己的 snapshot，commit 時偵測衝突，衝突則中止
- Snapshot metadata 採分層設計，避免數百萬檔案的表每次更新都要重寫完整檔案清單

I&#8217;ll focus only on the changes that I consider important to data operations and physical layout. Hive Problems Everything began at Netflix. Netflix relies on the lakehouse architecture. Before Iceberg, their data infrastructure centered around Hive. Data is stored in Parquet or Avro and abstracted under Hive tables, which are essentially sets of directories. A table is an HDFS folder; it can have partitions, which are inner sub-folders. A central place called the Hive Metastore manages table-to-folder tracking, including which folder the partition &#8220;2026-09-15&#8221; lives in. Netflix chose Hive because it was ubiquitous then; it was nearly the only option for the table format. However, Hive soon caused Netflix many problems, mostly because of the three Hive technical properties below. Transactional semantics mismatch Users can modify the information in the Hive Metastore transactionally because it&#8217;s backed by a transactional database (e.g., MySQL). The thing is, Hive was designed for HDFS, which is basically a filesystem, and filesystems don&#8217;t support transactional operations. With a transactional database, when writing A and B within a transaction, there are only two possible outcomes: both succeed or both fail. With a filesystem, because it doesn&#8217;t support transactions, writing A and B could result in a situation where only A or only B is written. The data-writing process could fail mid-write and leave you with a 150/1000-row CSV file. Because of this mismatch in transaction semantics, users must acquire locks on the Hive Metastore to safely allow multiple users to modify the table. A writer can change a table only if it has the lock. Everybody else waits. File listing To read any Hive table or partition, the query engine must do the file listing first. If a table has many files, this listing can take a long time. Netflix once shared that they had to wait more than 9 minutes just for query planning because Hive partitions contain many files. The problem is even worse when Netflix moved the data lake to object storage, which is famously known for expensive listing operations (they&#8217;re network calls, and they cost you) Unoptimized layout Object storage differs from a hierarchical filesystem. It&#8217;s flat and doesn&#8217;t physically support &#8220;directory&#8220;. The &#8220;country&#8220; or &#8220;year&#8220; you see in &#8220;bucket/country/year/object&#8220; is not a directory. It&#8217;s a prefix of your objects. Cloud object vendors such as AWS suggest that users distribute the read operations by using as many different prefixes as possible. This helps the vendor spread reads across servers, improving the throughput. This is against Hive&#8217;s design. When moving to object storage, Hive stores data for the same partitions in the same prefixes. When users issue a partition read, all object requests hit the same server, which caps throughput. Iceberg, day 1 The challenges above caused Netflix data users many correctness and performance problems. The engineering teams led by Ryan Blue (Tabular&#8217;s CEO) decided to develop a new table format; the new one must: Ensure end-to-end correctness: data read/write, schema evolution, everything. Achieve higher performance: No locking: many writers can write to the table at the same time. Skipping file listings. So they developed Iceberg. Iceberg fixes the problems by: Implementing optimistic concurrency control (OCC, no locking) instead of pessimistic concurrency control (PCC, locking); writes have their own table snapshot, add changes without locking, and then commit; conflicts are detected here; if it conflicts, it will be aborted. M ore clever metadata can skip file listing, support better file pruning, and enable safe data management features such as schema evolution or time travel. So, let&#8217;s talk about the Iceberg metadata layer. Netflix designed Iceberg to solve Hive's file-listing problem. Netflix&#8217;s approach is straightforward: track every file explicitly over time as snapshots. A snapshot is a complete listing of every file in the table at some point in the table history. If any users want to update the table, they will have their own snapshot, make changes, form the new snapshot, then atomically &#8220;tell&#8221; the system this is the &#8220;current snapshot of the table&#8220;, only then is that snapshot exposed to all other users. This is called snapshot isolation (SI). OCC&#8217;s common in database management, but Iceberg, Delta Lake, and Hudi are the first to implement it for table formats. SI is also best suited to object storage, since objects are immutable. Iceberg handles all table changes by adding new files. New files contain new rows, updated rows, and re-added files contain everything except the deleted rows. &#8212; But here is the catch: snapshots can&#8217;t be a single file that lists every data file. If a table has 5 million files and you need to make a new snapshot, you have to write down 5 million files again, plus your new file. So Iceberg&#8217;s snapshot metadata is layered instead.
