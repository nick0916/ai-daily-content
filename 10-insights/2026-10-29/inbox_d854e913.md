## Why a One-Line Change Can Break Your Whole Stack - Cole Gannaway, Qodo

程式碼生成變快後，瓶頸移到 PR 審查，需要有全局脈絡且獨立於寫碼 agent 的審查層。

**Why** 一行改動表面上建置與測試都通過，卻可能影響多個 repo；現場多數人都承認曾在沒看完所有程式碼的情況下合併 PR。

**How** 建立跨 repo 的軟體圖（software graph）與整合介面來呈現影響範圍（blast radius）；把自訂規則與部落知識帶入審查，並從 PR 留言建議新規則；審查 agent 與實作 agent 分開，可用不同模型與 harness 以降低偏見；也可在生成過程中的 25%、50%、75% 時機跑審查。

**What** Qodo 解決方案工程師在 AI Engineer 的演講，以開源密碼管理器 Bitwarden 的一行資料模型改動為例，說明其影響後端、網頁、行動、CLI 與 MCP。Qodo 整合 Jira、Linear 工單以標出需求缺口，並可透過 MCP、CLI 在寫碼前提供資訊；演講中未提供量化成效數據。

### 重點
- 審查 agent 應與寫碼 agent 分離：實作 agent 的 context 已被除錯、探索程式碼占用，且同一模型與 harness 有偏見；可用不同模型或對抗式審查者，結論一致為高信號，差異大則需深入調查
- 用軟體圖呈現跨 repo 影響範圍（blast radius），再搭配自訂規則（例如改動公開 API 須加 deprecation flag），並把 PR 留言轉成可重用的組織規則
- 做法：在生成過程的 25%、50%、75% 以 skill 觸發審查，讓審查 agent 像 manager 一樣導正偏離或過度工程；工單接入後可標出需求缺口
